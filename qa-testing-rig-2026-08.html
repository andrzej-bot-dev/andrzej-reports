🏆 TL;DR

Masz już 90% sprzętu: Mac M1 Pro (symulatory iOS + podpisywanie + host) + Pi5 + telefon Android (rig z raportu #1). Do tego Maestro (open source) jako jeden framework na obie platformy i numer Twilio do OTP. Koszt miesięczny: ~0 kr. BrowserStack odpowiednik: $150/mies.

  • Framework: Maestro 2.8.2 (Apache 2.0, YAML flows, cli z 2026-08-27) — tapOn, openLink (deep linki!), clearState (reset apki do czystego stanu!), assertVisible, takesScreenshot, retry (anty-flaky), startRecording (wideo z testu). Jeden plik YAML → iOS i Android.
  • Mac M1 Pro = serce rigu: host Maestro + iOS symulatory (za darmo, simctl erase = pełny reset, kilka równolegle) + podpis WDA/TestFlight + Android emulator (obrazy ARM na Apple Silicon). Fast loop testowy: minuty, nie godziny.
  • Fizyczne urządzenia tylko tam gdzie muszą być: attribution (GAID/IDFA, Install Referrer wymaga sklepu), OTP z prawdziwym SMS, universal links.
  • OTP: numer wirtualny Twilio — apka wysyła kod na numer +46 → skrypt czyta kod przez Twilio API → wpisuje w apkę przez Maestro. Działa identycznie na iOS i Androidzie.

🔗 Deep linki — konkretne przepisy

Android

# scheme / app link:
adb shell am start -W -a android.intent.action.VIEW \
  -d "myapp://product/123" com.example.app

# czy app links zweryfikowane (assetlinks.json):
adb shell pm verify-app-links com.example.app

# który handler łapie intent (bez uruchamiania):
adb shell cmd package resolve-activity --brief \
  -a android.intent.action.VIEW -d "https://example.com/x"

developer.android.com/training/app-links · tools/adb#am-start

iOS

# symulator:
xcrun simctl openurl booted "myapp://product/123"

# real device (WDA przez USB):
curl -X POST http://localhost:8100/session/$SID/url \
  -d '{"url": "https://example.com/path"}'

# albo przez Appium capability:
"deepLinkUrl": "https://example.com/path"

# w Maestro po prostu:
openLink: "https://example.com/path"

WDA wiki (Queries) · appium docs · simctl docs

Na realnym iPhonie NIE MA odpowiednika am start — jedyna droga to WDA /wda/url (potrzebny działający WDA z raportu #2). Na symulatorze wszystko proste. Custom scheme vs Universal Link: UL trudniejsze w debugowaniu (wymaga apple-app-site-association na domenie; FB/X Messenger potrafią łamać UL → fallback do Safari).

🎯 Attribution testing — workflow "reset stanu + instalacja z linka"

Android (rig na Pi, pełna automatyzacja)

  1. Dezynstalacja: adb uninstall com.example.app
  2. Reset identyfikatorów reklamowych: GAID: Ustawienia → Google → Reklamy → "Resetuj identyfikator reklamowy" (+ wyłącz personalizację) — najpewniej przez adb shell am start deep-link do ekranu ustawień + tap (uiautomator2), bo GAID nie ma bezpośredniego polecenia adb
  3. Instalacja Z LINKA: otwórz https://play.google.com/store/apps/details?id=com.example.app&referrer=utm_source%3Dtest%26utm_campaign%3Dqa — klik "Install" automatyzujemy tapami (uiautomator2) albo przez market://details?id=...&referrer=...
  4. Pierwsze uruchomienie: apka przez bibliotekę installreferrer:2.2 czyta getInstallReferrer() → weryfikujemy w logach SDK / ekranie
  5. Weryfikacja SDK: AppsFlyer: tryb dev + logi af (dev.appsflyer.com/harness) · Adjust: sandbox mode · Branch: Liveview

iOS (17e przez Mac/WDA)

  1. Dezynstalacja + reset IDFA: Ustawienia → Prywatność → Śledzenie → wyłącz/włącz (reset przy wyłączeniu) — tapujemy przez WDA; ATT prompt obsłużony w teście
  2. Instalacja z App Store link (tap automation przez WDA) albo TestFlight build dla dev-flow
  3. Uwaga SKAdNetwork: konwersje przychodzą z opóźnieniem — do QA używać postbacków testowych (AppsFlyer/Adjust mają tryby testowe)

developer.android.com/google/play/installreferrer · dev.appsflyer.com · help.adjust.com · Branch docs — pełne URL-e w destillacie deeplink-attr.md

🚀 Wdrożenie (kolejność sensowna)

  1. Mac (30 min): brew install maestro → maestro start-device ios (simulator) → pierwszy flow YAML na symulatorze → xcrun simctl erase/reuse
  2. Android emulator na Macu (30 min): Android Studio → AVD ARM (API 33-35, Play image) → Maestro wskazuje emulator
  3. Rig Android z raportu #1 (już zaprojektowany): telefon na USB do Pi, adb, uiautomator2 — dokładamy: skrypt reset GAID + Play install z referrerem + weryfikacja logów
  4. iPhone real (z raportu #2): Mac + WDA + (ewentualnie 17e) — deep linki przez /wda/url, IDFA reset flow
  5. Twilio (15 min): numer +46, klucz API, skrypt get-last-sms.py → wpiąć do flow OTP
  6. CI lekkie: cron na Pi/Macu: maestro test flows/ --format junit → wyniki na Discord (ja raportuję)

Co dostaję ja: mogę sam pisać flow YAML, odpalać je przez ssh na Macu/Pi, zbierać screenshoty/wideo i raportować na Discord — czyli "test apki" staje się komendą w czacie.
