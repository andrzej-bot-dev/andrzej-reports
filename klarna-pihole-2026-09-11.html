1 · Background & scope

Klarna AB is a Swedish bank & BNPL provider. The question: do typical Pi-hole setups break any Klarna feature or page? This follows up our July 2026 analysis of l.klarna.com and the DNS-blocker comparison, now with a full audit of all Klarna-facing domains and hands-on Pi-hole v6 experiments.

Test date: 2026-09-11. Klarna domains were inventoried via certificate transparency (crt.sh), live DNS, blocklist greps, GitHub issue reports by Klarna staff, and HTTP probes.

3 · How Pi-hole actually blocks (the three rules that decide everything)

All three verified live on our lab Pi-hole v6.4.3 / FTL v6.7 (Docker, upstreams 1.1.1.1 + 8.8.8.8, blocking mode NULL → 0.0.0.0, CNAMEdeepInspect = true default):

Rule 1 — Plain domain/hosts lists are EXACT-match only

With StevenBlack (contains appsflyer.com): appsflyer.com → 0.0.0.0 ✅ blocked, but www.appsflyer.com → resolves normally. Subdomains of a listed domain are not blocked. This is why Klarna's chain target getklarna.customlinks.appsflyer.com survives most lists.

Rule 2 — CNAME deep inspection works — if a chain member matches

Pi-hole (FTL ≥ v5.14, default-on) inspects upstream CNAME chains. Empirical test: adding the exact entry getklarna.customlinks.appsflyer.com to gravity (simulating 1Hosts Lite) → l.klarna.com → 0.0.0.0 — the whole chain is killed, while klarna.com control still resolves. Verified for gravity, manual denylist and regex alike.

Rule 3 — Adblock-format lists (||domain^) DO cover subdomains

Pi-hole v6 supports Adblock-syntax adlists (the format HaGeZi recommends for Pi-hole). Test: a one-line list ||appsflyer.com^ → getklarna.customlinks.appsflyer.com → 0.0.0.0 → l.klarna.com → 0.0.0.0. This is how HaGeZi Pro++/Ultimate break Klarna's link domain on Pi-hole.

⚠️ Methodology gotcha (cost us an hour): deep inspection runs at resolution time. Answers already in dnsmasq's cache are served without re-inspection, and pihole flush clears only the query log, not the DNS cache. Always full-restart before testing. Our first "chain passes" results were cache artefacts.

5 · The l.klarna.com story (why this one domain is special)

l.klarna.com is Klarna's branded AppsFlyer OneLink host. Live chain: l.klarna.com → getklarna.customlinks.appsflyer.com → onelinkalbnew.onelink.me.cdn.cloudflare.net → A. Klarna staff describe it as "Klarna's own first-party branded link domain used for login (Sign-in on klarna.com and app.klarna.com/login), marketing emails, push, and CRM deep-linking" — example CTA link: l.klarna.com/22XC?pid=KlarnaCom&c=DE.Klarnacom.Homepage.FloatingCTA.

  • Jul 2026: Klarna engineer files unblock requests across the ecosystem. HaGeZi removes l.klarna.com from his referral list (hagezi#10901, fixed in release 37522026.203.69543) while noting NextDNS still kills it via the CNAME. AdGuard verifies their DNS doesn't block it (AdGuardSDNSFilter#2089, closed 2026-08-20).
  • NextDNS: still blocked today — customlinks.appsflyer.com entry + CNAME uncloaking + subdomain matching. Klarna asks for a per-alias exception like AdGuard's paymaya precedent (nextdns#26, open).
  • Pi-hole nuance (this report): outcome depends on list format — exact-match lists leave it working; Adblock-format lists with ||appsflyer.com^ (HaGeZi Pro++/Ultimate) or exact chain-target entries (1Hosts Lite) hard-block it via deep inspection.

7 · Recommendations

  • If Sign-in CTA or email links break on your Pi-hole: whitelist the chain member, not just the alias — allow getklarna.customlinks.appsflyer.com (regex (^|\.)getklarna\.customlinks\.appsflyer\.com$) or simply l.klarna.com. Deep inspection then passes the chain (verified).
  • HaGeZi users: Light/Normal/Pro keep Klarna 100% functional. Pro++/Ultimate trade Klarna's tracked links for tracker coverage — combine with the whitelist above if you click Klarna emails.
  • Don't run referral lists network-wide (HaGeZi wiki's own advice) — they exist for per-device browser blocking.
  • visbymaklarna.se is a false positive worth reporting upstream (legit Gotland real-estate agency, blocked in HaGeZi Normal→Ultimate).
  • Browser-level blockers (uBlock/EasyPrivacy) treat many of these domains differently — DNS conclusions here don't transfer 1:1.

8 · Appendix

A · Reproduce the three experiments

# Rule 1 — exact-match only (StevenBlack gravity)
dig @pihole appsflyer.com A        # → 0.0.0.0
dig @pihole www.appsflyer.com A    # → real IPs (subdomain survives)

# Rule 2 — CNAME deep inspection (1Hosts-style exact entry in gravity)
pihole deny getklarna.customlinks.appsflyer.com
docker restart pihole              # cache! (pihole flush ≠ cache flush)
dig @pihole l.klarna.com A         # → 0.0.0.0 (whole chain killed)

# Rule 3 — Adblock-format wildcard semantics
echo "||appsflyer.com^" > list.txt  # add as adlist → gravity
dig @pihole l.klarna.com A         # → 0.0.0.0

B · Lab incident (worth knowing for any Pi-hole Docker user)

Our lab Pi-hole's DNS had been silently dead since 06:10 the same day: FTL logged dnsmasq: failed to create listening socket for port 53: Address in use while web UI and NTP kept running. Culprit: lxc-net's dnsmasq (10.0.3.1:53) left enabled. Fix: systemctl stop lxc-net && systemctl disable lxc-net + container restart. Symptom signature: web UI fine, port 53 UDP bound but every query times out.
